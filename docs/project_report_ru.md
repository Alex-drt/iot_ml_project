# Отчёт по проекту IoT Failure Prediction

**Дата анализа:** 2 ноября 2026 г.  
**Область:** подготовка данных, код экспериментов, доступные результаты SCANIA Component X и CICIoMT2024, проверка тестов проекта.

## 1. Краткий вывод

Проект реализует воспроизводимый экспериментальный pipeline: подготовка
табличных данных, проверка train/validation/test, обучение нескольких
классификаторов, сохранение метрик и артефактов. Это исследовательский
прототип, а не система прогнозирования в эксплуатации.

- **CICIoMT:** MLP повторно обучен на полном capture-grouped разбиении
  (3 seeds, CUDA). Средние accuracy 99,57%, balanced accuracy 96,09%,
  macro F1 95,38%; новый результат приведён ниже. Старый запуск сохранён
  для сравнения и не удалялся.
- Бинарный порог по умолчанию выбирается по balanced accuracy, а не F1,
  чтобы меньше зависеть от prevalence validation; это не заменяет
  deployment-порог, заданный стоимостью тревог/пропусков.
- **SCANIA:** ни одна из запущенных моделей не решает надёжно
  пяти-классовую задачу. В CLI теперь реализовано cost-sensitive решение
  по официальной матрице challenge; проверка сохранённых class scores
  показывает снижение среднего cost, но редкие классы всё ещё требуют
  отдельной оценки.
- Для SCANIA добавлена подготовка полных temporal sequence splits и
  endpoint-оценка LSTM-AE. Первый прогон подтверждает технический запуск,
  но пока не обнаруживает отказы лучше случайного ранжирования.
- **GPU:** CUDA действительно использовалась для SCANIA MLP. На небольшом
  SCANIA наборе GPU оказался медленнее CPU; эти замеры не означают, что GPU
  не полезна на больших данных.
- Полный набор тестов проекта в настроенном `.venv-1` прошёл:
  **63 теста, 2 пропуска**.

## 2. Состав проекта и методика

| Компонент | Назначение |
|---|---|
| `scripts/prepare_scania.py` | Сбор train/validation/test SCANIA, формирование целевых классов и списка признаков |
| `scripts/prepare_ciciomt.py` | Сбор CSV CICIoMT по манифесту, проверка путей, схемы, разбиения и классов |
| `iot_experiment.py.py` | Проверка входов, preprocessing, обучение, threshold selection, метрики и сохранение артефактов |
| `scripts/analyze_dataset.py` | Анализ распределений, пропусков и признаков, построение графиков |
| `scripts/run_gui.py` | Tkinter-интерфейс для подготовки и запуска экспериментов |
| `tests/` | Регрессионные и smoke-тесты на небольших fixtures |

Доступны Logistic Regression и Random Forest на CPU, MLP на CPU/CUDA, а
также LSTM autoencoder для бинарных временных рядов. CICIoMT CSV в текущей
подготовке не имеют подтверждённых sequence/time semantics; применять к
ним LSTM-AE по порядку строк нельзя.

Каждый эксперимент сохраняет аргументы, хэши входных данных, окружение,
статус, результаты по seed, предсказания, preprocessing и модель.
`--validate-only` проверяет данные до обучения. Существующий output
каталог не перезаписывается.

### Архитектура и вычисления

Архитектура разделяет подготовку наборов, общий экспериментальный CLI,
описательную аналитику, GUI и тесты. Проверенные решения: preprocessing
fit выполняется только на train; пропуски заменяются train-медианами,
после чего признаки стандартизуются; Logistic Regression и Random Forest
используют class weighting; MLP обучается с обратными частотами классов.
Бинарный threshold теперь выбирается по balanced accuracy (F1 можно
запросить через CLI). Для SCANIA `--scania-cost` выбирает класс с
минимальным ожидаемым cost по class scores; обычный режим остаётся
`argmax`. MLP сохраняет состояние с минимальной validation cross-entropy,
а LSTM-AE — с минимальной reconstruction error на нормальных validation
окнах.
Метрики по всем трём CICIoMT seeds независимо пересчитаны из сохранённых
`test_predictions.csv`; accuracy, balanced accuracy, macro F1, ROC-AUC,
average precision и confusion matrix совпали с JSON без численного
расхождения.

Сохранённый CICIoMT MLP run обучался 20 эпох, но лучший checkpoint выбран на эпохах
1, 2 и 2 для seeds 11, 22 и 33. Это не доказательство ошибки реализации,
но важный диагностический признак: выбранная validation-схема
profiling + held-out attacks может плохо отражать train/test, а
checkpoint selection и threshold calibration зависят от неё.

Главное ограничение вычислительной архитектуры — весь CSV split читается
в память; preprocessing и обучение далее создают дополнительные
представления массивов. Pipeline не out-of-core. Текущие 5,58 млн строк
CICIoMT удалось обработать на локальной машине, но память и время будут
расти с набором данных и числом признаков. `iot_experiment.py.py` и
`scripts/run_gui.py` содержат крупные концентрации логики; для дальнейшего
развития полезно выделять модель, метрики, подготовку и GUI в меньшие
модули, сохраняя текущие CLI-контракты.

Надёжность CICIoMT подготовки имеет отдельный риск: каталог результата
создаётся до обработки всех chunks, а CSV дописываются по ходу обработки.
При ошибке в позднем capture (например, несовпадение source label или
некорректное числовое значение) остаются неполные файлы в output-каталоге,
который следующий запуск уже не сможет создать повторно. Стоит писать во
временный sibling-каталог и публиковать его только после полной валидации
либо явно документировать ручное удаление именно неполного каталога.

## 3. Данные и подготовка

### 3.1 SCANIA Component X

Подготовленный набор для исходных запусков:
`datasets/processed/scania/prepared_20261101_203615`.
Используются 105 операционных признаков. Подготовщик объединяет таблицы по
`vehicle_id`; спецификации компонентов не включены. В стандартном режиме
train оставляется одно допустимое наблюдение на автомобиль;
validation/test используют последнее наблюдение и поставленные классы.
Классы train выводятся из оставшегося времени по границам, описанным в
руководстве.

| Split | Строк | Класс 0 | Класс 1 | Класс 2 | Класс 3 | Класс 4 |
|---|---:|---:|---:|---:|---:|---:|
| Train | 23 549 | 22 924 (97,35%) | 288 | 174 | 70 | 93 |
| Validation | 5 046 | 4 910 (97,30%) | 16 | 14 | 30 | 76 |
| Test | 5 045 | 4 903 (97,19%) | 26 | 15 | 41 | 60 |

Класс 0 соответствует readout'ам более чем за 48 time units до ремонта
либо здоровому компоненту без ремонта в течение наблюдаемого периода;
классы 1–4 описывают последовательные окна 48–24, 24–12, 12–6 и 6–0
до первого ремонта. Это подтверждено challenge specification и статьёй
о датасете в архиве. Censored readout с горизонтом до конца наблюдения
<=48 не получает искусственную метку класса 0, а исключается; readout
после первого ремонта также исключается. В test только 142 наблюдения из
5 045 относятся к классам 1–4. Validation/test — случайно выбранные
последние readout'ы с supplied labels, построенными по тем же временным
окнам. Это пяти-классовая классификация, не survival analysis и не
регрессия остаточного срока службы.

Дополнительно проверено, сколько сигнала отбрасывает режим подготовки
подготовки. В исходных train-таблицах 1 122 452 операционных readout;
после правил eligibility остаётся 919 315 строк от тех же 23 549
автомобилей. Распределение этих строк: класс 0 — 893 575, класс 1 —
12 503, класс 2 — 6 179, класс 3 — 3 200, класс 4 — 3 858. Стандартный
режим случайно оставляет только один readout на автомобиль (23 549 строк),
поэтому теряется большая часть наблюдений близко к отказу. Все допустимые
readout'ы сохраняются в режиме `all_eligible_readouts`, который теперь
используется по умолчанию; режим `one_per_vehicle` оставлен для
сравнительного эксперимента. Это не увеличивает число независимых
автомобилей и сохраняет все временные наблюдения автомобилей только в
train. Проверка подтвердила отсутствие пересечения
`vehicle_id` между train, validation и test. Разделение по автомобилям
предотвращает прямую утечку групп, но не устраняет корреляцию readout'ов
внутри train. В каждом из классов 1–4 есть наблюдения от 1 923–2 232
разных обучающих автомобилей; эти множества могут пересекаться.

### 3.2 CICIoMT2024 Wi-Fi/MQTT

Для подготовленного набора использованы 110 локальных CSV: 47 attack
captures из train, 21 из официального test и 42 из profiling. Так как
схемы attack и profiling CSV различаются, оставлены 38 общих признаков.
Манифест направляет семь train attack captures в validation; остальные
train captures остаются в train. Все official test captures оставлены
только в test. 42 profiling captures используются как отрицательные
(benign) примеры для validation.

| Split | Строк | Класс 0 (benign) | Класс 1 (attack) |
|---|---:|---:|---:|
| Train | 5 580 694 | 192 732 (3,45%) | 5 387 962 (96,55%) |
| Validation | 1 528 190 | 389 956 (25,52%) | 1 138 234 (74,48%) |
| Test | 1 614 182 | 37 607 (2,33%) | 1 576 575 (97,67%) |

Для исправления source shift подготовлен новый split
`datasets/processed/ciciomt/prepared_grouped_20261102`: 34 целых profiling
captures распределены в train, 8 других captures — в validation; ни один
capture не разделяется между split. Его размеры: train 5 732 675
(344 713 benign, 5 387 962 attack), validation 1 376 209
(237 975 benign, 1 138 234 attack), test 1 614 182
(37 607 benign, 1 576 575 attack). Доли benign составляют 6,01%, 17,29%
и 2,33% соответственно. Validation теперь содержит profiling captures,
похожий источник benign есть и в train, однако prior shift и отсутствие
official validation сохраняются. Реальный MLP на этом новом split ещё не
переобучался; архивные CICIoMT метрики ниже к нему не относятся.

**Ограничения split и меток:**

1. Validation из profiling не является официальным validation split
   атакующего набора и может иметь domain shift относительно train/test.
   Модель может различать тип источника/capture, а не только benign и
   attack признаки.
2. В attack CSV нет встроенных построчных столбцов target/label; метка
   задаётся на уровне capture. Архивные документы описывают attack captures
   в `attacks` и обычные active/idle/power/interaction profiling captures;
   файл `Benign_train` явно отмечен как benign. Поэтому `attack=1`,
   `benign/profiling=0` в манифесте согласуется с provenance архива, но
   остаётся capture-level mapping, не независимой packet-level разметкой.
3. Перепроверка 197 совпадающих уникальных feature-векторов точным
   сравнением подтвердила совпадение всех 38 числовых признаков. Им
   соответствуют 359 test-строк; все они относятся к классу attack, и
   совпавшие train-векторы также имеют метку attack. Это не
   межклассовая утечка метки, но дублирование между split нарушает
   строгую уникальность test-объектов и требует установить происхождение
   повторяющихся flows.
4. В validation обнаружены 20 исходных пропусков и 265 бесконечных
   feature-значений; эксперимент преобразует бесконечности в пропуски.
   Train/test в аудите не содержат пропусков.
5. Группировка по capture препятствует распределению одного файла между
   split, но сама по себе не доказывает статистическую независимость.

По описательной аналитике SCANIA нашлось 7 014 / 2 472 645 пропусков в
train-ячейках признаков (0,284%), 1 519 / 529 830 в validation (0,287%)
и 1 655 / 529 725 в test (0,312%); бесконечных значений нет. На
равномерных выборках для графиков (до 10 000 строк на split) отдельные
SCANIA признаки показывают заметное сдвижение train–validation средних
(максимальный стандартизованный разрыв около 1,89) и validation–test
(около 1,60). Эти оценки описательные и смешивают эффект различия
целевых классов и распределений; они не являются тестом статистической
значимости.

Конфигурации лежат в `configs/ciciomt_features.json` и
`configs/ciciomt_manifest.csv`. В
`datasets/processed/ciciomt/prepared_v1/preparation.json` записаны
происхождение файлов, размеры и хэши. Mapping подтверждён как
capture-level интерпретация архивной структуры; profiling validation
по-прежнему не является официальным validation split атакующего набора.

## 4. Экспериментальные результаты

### 4.1 CICIoMT — MLP, CPU

Завершён исторический запуск `results/ciciomt/mlp_20261102_133329`: seeds 11, 22, 33;
20 эпох, batch 256, hidden size 64. В окружении эксперимента использованы
Python 3.15.0 и PyTorch 2.15.0+cu132, но в аргументах явно указан `device=cpu`.
Средние значения и `sample_std` ниже рассчитаны по трём seed; это разброс
на одном фиксированном split, а не доверительный интервал. Это архивный
запуск с прежним profiling-only validation и подбором порога по F1;
изменения threshold по balanced accuracy и capture split ещё не оценены
новым полным CICIoMT MLP run.

|---|---:|

| Balanced accuracy | 99,086% ± 0,768 п.п. |
| Macro F1 | 95,732% ± 0,392 п.п. |
| Precision класса attack | 99,966% ± 0,037 п.п. |
| Recall класса attack | 99,607% ± 0,041 п.п. |
| ROC-AUC | 0,99954 ± 0,00008 |
| False-positive rate | 1,435% ± 1,556 п.п. |

| Время fit на seed | 829,2 ± 7,8 с |

Усреднённая по seed матрица ошибок (поэтому значения не целые):

| | Предсказано benign | Предсказано attack |
|---|---:|---:|
| Фактически benign | TN ≈ 37 067 | FP ≈ 540 |
| Фактически attack | FN ≈ 6 191 | TP ≈ 1 570 384 |

Контекст важен: baseline «всегда attack» получает 97,67% accuracy только
из-за prevalence test, но его balanced accuracy равна 50%, macro F1 —
49,41%, а false-positive rate — 100%. MLP лучше этого baseline по
balanced accuracy и macro F1. При этом результат threshold заметно
зависит от seed: пороги F1 на validation равны примерно 0,590, 0,969 и
0,886; соответствующие false-positive counts на test — 1 171, 433 и 15.
Такой разброс вместе с profiling-based validation требует проверки на
validation, репрезентативной для реального deployment-сценария. AP также
следует интерпретировать с учётом того, что 97,67% test — атаки.
Кроме того, доля benign в validation составляет 25,52%, против 3,45% в
train и 2,33% в test. Поскольку F1 и выбранный по нему threshold зависят
от prevalence, profiling-based validation может калибровать точку
решения не под целевой test/deployment prevalence. Необходимо сначала
зафиксировать deployment-условия, затем подобрать representative
validation; official test оставить для финальной оценки.

|---|---:|

| Balanced accuracy | 96,093% ± 1,058 п.п. |
| Macro F1 | 95,380% ± 0,190 п.п. |

Усреднённая матрица ошибок: TN ≈ 34 765, FP ≈ 2 842, FN ≈ 4 052,

capture-grouped validation и balanced-accuracy-порог; поэтому это не

benign prevalence нового validation равна 17,29%, тогда как в test она
2,33%. Несмотря на улучшенную группировку, validation всё ещё не
репрезентирует эксплуатационную частоту benign. Нельзя трактовать
test-метрики как гарантию deployment-качества; для неё нужна
представительная validation и заранее заданная цена ложных тревог.

### 4.2.1 SCANIA — решение по официальной стоимости ошибок

Новое правило выбирает класс с минимальной ожидаемой стоимостью
`class_scores @ SCANIA_COST_MATRIX`. Оно не переобучает модель: метрики
ниже пересчитаны на сохранённых scores для тех же фиксированных split и
seed. На тесте средняя challenge cost снизилась у обеих моделей, но
balanced accuracy и macro F1 ухудшились; это ожидаемый компромисс, а не
улучшение всех метрик.

| Модель | Правило | Accuracy | Balanced accuracy | Macro F1 | Mean cost |
|---|---|---:|---:|---:|---:|
| Logistic Regression | argmax | 23,90% | 25,33% | 9,31% | 11,34 |
| Logistic Regression | minimum expected cost | 1,45% | 19,72% | 0,58% | 9,91 |
| MLP | argmax | 26,61% | 23,04% | 9,39% | 11,34 |
| MLP | minimum expected cost | 4,80% | 19,65% | 1,89% | 9,85 |

Следовательно, cost-sensitive правило имеет смысл только при выборе
официальной функции стоимости как основного deployment-критерия.
Вероятностные scores моделей отдельно не калибровались; оценки стоимости
нужно рассматривать как диагностическое сравнение, а не эксплуатационную
гарантию.

### 4.3 SCANIA — все допустимые обучающие наблюдения

Проверен отдельный режим подготовки со всеми 919 315 допустимыми
обучающими readout'ами вместо случайного выбора одного на автомобиль.
Validation/test оставлены без изменений; использованы тот же MLP, CPU,
20 эпох, batch 256, hidden size 64 и seeds 11, 22, 33. Этот эксперимент
сопоставляет две стратегии подготовки на том же vehicle-level split, но
не увеличивает число независимых автомобилей. Разброс ниже — только между
seed на фиксированных данных.

| Метрика на test | Среднее ± sample std |
|---|---:|
| Accuracy | 26,61% ± 13,95 п.п. |
| Balanced accuracy | 23,04% ± 3,52 п.п. |
| Macro F1 | 9,39% ± 3,77 п.п. |
| Время fit на seed | 126,88 ± 1,71 с |
| Инференс 5 045 строк | 0,0080 ± 0,0005 с |

Accuracy выросла относительно MLP на одном readout на автомобиль, однако
balanced accuracy осталась около 23%, macro F1 — ниже baseline,
предсказывающего только класс 0 (19,71%). Seed 33 дал macro F1 13,69%,
тогда как seeds 11 и 22 — 6,68% и 7,78%; такая нестабильность не
позволяет считать прирост надёжным. На трёх test-seed precision редких
классов не превышала 1,92%, а recall класса 3 колебался от 0 до 2,4%.
В test всего 15 объектов класса 2 и 41 класса 3.

Это исследовательский результат, а не исправленная оценка качества:
training target рассчитывается по time-to-event на каждом readout,
тогда как validation/test используют предоставленные per-vehicle метки
на последнем readout; эквивалентность этих target без первичной
документации не установлена. Выбор лучшей эпохи также зависит от
validation с малыми support редких классов. До независимой сверки меток
и назначения классов более сложные модели или настройка по test не
обоснованы.

### 4.4 SCANIA — CPU против GPU

Сопоставлялись одинаковые MLP-параметры, seeds и входные hashes. На этом
маленьком наборе CPU быстрее:

| Устройство | Fit на seed | Инференс 5 045 test строк | Macro F1 |
|---|---:|---:|---:|
| CPU | ≈ 2,67 с | ≈ 0,0066 с | 6,98% |
| CUDA, NVIDIA GeForce RTX 4060 Ti | ≈ 4,38 с | ≈ 0,0100 с | 6,88% |

В этих запусках CUDA была действительно активна (`torch 2.15.0+cu132`,
CUDA runtime 13.2). Небольшой объём работы не компенсирует передачу данных
и накладные расходы GPU; это не benchmark для CICIoMT и не обобщается на
более крупные задачи.

### 4.5 SCANIA — LSTM autoencoder на временных рядах

Добавлены отдельные sequence CSV: train хранит все допустимые readout'ы,
validation/test — все измерения автомобилей, с бинарной меткой
`anomaly_target = (class_label > 0)`. Поскольку validation/test labels
заданы на уровне автомобиля, оценивалось только последнее полное окно;
окна короче 10 readout'ов исключены. При `window=10` в test оценены
4 625 из 5 045 автомобилей (91,7%). В train из 687 727 нормальных окон
перед обучением равномерно отобрано не более четырёх на автомобиль.

Запуск: CUDA, RTX 4060 Ti, 20 эпох, hidden size 32, latent size 8, 3 seed.
Checkpoint выбирался по минимальной reconstruction error на нормальных
validation-окнах, threshold — 99-й перцентиль той же ошибки. Средние test
метрики: balanced accuracy **50,63%**, macro F1 **50,56%**, ROC-AUC
**0,518 ± 0,004**. Среди 138 положительных автомобилей модель нашла
только 2 (recall **1,45%**), при 7–10 ложных тревогах на seed. Это
подтверждает корректный запуск sequence pipeline, но не полезное
обнаружение отказов; текущие признаки/окна/цель не дают сигнал лучше
случайного ранжирования.

В результатах есть отдельный SCANIA MLP запуск с train preparation seed
100 и другим train hash (`c8aa58e3…` вместо `bc37fe99…`). Его метрики не
объединены с основным CPU/GPU сравнением: случайный выбор наблюдения на
автомобиль изменил состав обучающих классов. Это подтверждает, что seed
подготовки данных — самостоятельный фактор эксперимента.

## 6. Основные ограничения

- SCANIA train/validation/test имеют сильный дисбаланс, а подготовка
  исключает censored readout'ы с горизонтом менее 48 единиц и post-event
  readout'ы; обучающие строки одного автомобиля коррелированы.
- Эксперимент со всеми обучающими readout'ами увеличил число строк, но не
  число независимых автомобилей; качество редких классов осталось низким.
- CICIoMT profiling captures теперь можно разделять между train и
  validation целиком по source_id, но это не официальный attack validation
  и не устраняет разницу со сценариями эксплуатации. Метки остаются
  capture-level, а не встроенной построчной разметкой.
- Balanced-accuracy threshold меньше зависит от prevalence, но всё равно
  переносится с validation на deployment; целевой уровень false alarms и
  стоимость пропуска нужно задать отдельно.
- CIC feature overlap на уровне строк/векторов требует расследования.
- Три seed оценивают только вариативность обучения на фиксированных
  данных. Они не дают независимых повторов датасета и не являются
  доверительным интервалом.
- В проекте не зафиксированы метрики эксплуатационных затрат, стоимость
  пропуска/ложной тревоги и требования к задержке/частоте тревог.
- SCANIA LSTM-AE теперь проверен на реальных временных рядах, но recall
  отказов около 1,45% и ROC-AUC близок к 0,5; это не рабочий детектор.
  CICIoMT остаётся неподходящим для LSTM без достоверной временной оси и
  sequence provenance.
- SCANIA характеристики элементов оборудования пока не используются;
  проект не решает задачу survival analysis.

## 7. Рекомендуемые следующие шаги

1. Сверить бинарное отображение CICIoMT, значения `Benign`/`Attack`,
   происхождение profiling и состав official partitions с первичным
   описанием dataset; сохранить ссылку/версию документации.
2. Запустить MLP на новом capture-grouped CICIoMT split и сравнить с
   прежним результатом; отдельно собрать deployment validation с целевой
   частотой benign/attack и заданной ценой false alarms. Не выбирать
   threshold и гиперпараметры по official test.
3. Проверить 197 совпадающих train/test feature-векторов на уровне
   исходных файлов и полных строк; при подтверждённых дублях определить
   split по capture/событию, а не удалять совпадения автоматически.
4. Для CICIoMT дополнительно публиковать confusion matrix, per-class
   recall, false-positive rate, alarms per fixed traffic volume и
   доверительные оценки на capture-level повторах; отдельно сравнить
   с простым baseline.
5. Для SCANIA использовать все допустимые обучающие readout'ы и решить,
   является ли официальная стоимость основной метрикой. Cost-sensitive
   правило снижает mean cost, но сильно уменьшает macro F1; одних
   балансирующих весов недостаточно для надёжной редкой классификации.
6. Для LSTM проверить альтернативные временные признаки/окна и
   event-target постановку на новых vehicle-level повторах; текущий
   endpoint эксперимент не даёт полезного recall отказов.
7. После методологической фиксации запустить независимые повторы и
   повторный benchmark на заранее указанном оборудовании; сохранить
   конфигурацию подготовки отдельно от seed модели.
